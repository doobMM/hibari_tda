사용자의 질문 하나(*"우리 코드가 정말 반영돼 있어?"*)가 **겉보기에 잘 돌아가던 페이지가

## 1. 배경 — 이 프로젝트가 무엇인가

사카모토 류이치의 곡 **〈hibari〉**(*out of noise*, 2009)를 **위상수학적 데이터 분석
(Topological Data Analysis, Persistent Homology)** 으로 분석해, 원곡과 **위상 구조가 유사한
음악을 생성**하는 연구다.

### 핵심 용어 (이 문서를 읽는 데 필요한 것만)

| 용어 | 뜻 |
|---|---|
| **note** | `(음높이, 길이)` 쌍. hibari 는 고유 note 가 **23개**다 |
| **고리 (H₁ cycle)** | PH 가 찾아낸 note 들의 순환 구조. hibari 에서 **14개** 발견됨 |
| **중첩행렬 (Overlap Matrix, OM)** | `시각 × 고리` 행렬. 각 시각에 어떤 고리가 "켜져" 있는지. **음악 생성의 씨앗** |
| **Algorithm 1** | 켜진 고리들에서 확률적으로 음을 뽑는 규칙 기반 생성기 (`generation.py`) |
| **JS divergence** | 원곡과 생성곡의 분포 차이. 낮을수록 원곡에 가깝다 |

### 생성 파이프라인

```
MIDI → 전처리 → Persistent Homology → 중첩행렬 → Algorithm 1 → 음악
```

### 왜 웹페이지를 만드나

연구를 **사람이 직접 만져 보게** 하려는 공개 트랙이 있다.
목표는 *"사람들이 의도에 맞게 음악을 생성하되, 그 생성이 위상수학과 hibari 의 구조에
기반하게 하는 것"* 이다. 단순 데모가 아니라 **연구의 메커니즘이 실제로 작동하는 장난감**이어야 한다.

## 2. 이 세션 직전 상태 — 여섯 번의 거절

상호작용 페이지를 여섯 번 만들어 **여섯 번 거절당한** 상태였다.

| 판 | 무엇 | 판정 |
|---|---|---|
| 1 | 제출 버튼 + 텍스트 힌트 | "이건 게임이 아니야, 즐겁지가 않잖아" |
| 2 | 그림자 맞추기 (α 축) | α 가 죽어 있어 미터가 100% 고정 |
| 3 | 높낮이/밀도 축 | "조작할 때마다 처음으로 돌아가는 게 목표에 어긋나" |
| 4 | `arena/` 파종장 (Elo 투표) | "방금 그 게임 재미없어" |
| 5 | `phase.html` (주기 손잡이) | "상당히 비직관적이야. **만지고 싶지도 않아**" |
| 6 | `motif.html` (모티브→고리) | "여전히 직관적이지 않아, 재미없어" |

### **[판단]** 실패를 증상이 아니라 *계급*으로 묶었다

여섯 판을 하나씩 고치는 대신 **공통 원인**을 찾았다.

- **1~3 은 기계적 고장** — 반응 없음 / 죽은 축 / 리셋. 전부 고쳤다.
- **4~6 은 같은 병** — **목표도 소유감도 없는 "샌드박스 + 설명"**.
  화면이 *무엇을 하는지*는 말해 주지만 *왜 계속하는지*는 답하지 않았다.
  **손잡이를 주고 그 뜻을 글로 설명하는 물건은 전부 거절당했다.**

그리고 놓치고 있던 단서를 찾았다 — 이 프로젝트에서 **유일하게 긍정된 산출물은 음악 자체**였다:

> *"초기 생성곡들도 퀄리티가 나쁘지 않아, 템포가 느리기 때문이야.
> hibari 원곡과 분위기가 비슷해서 영화 〈괴물〉에 어울릴만한 곡들이야."*

인터페이스가 아니었다. → **인터페이스를 재미있게 만들려 하지 말고,
좋은 소리가 즉시 나게 하고 인터페이스는 사라지게 한다.**

그 결론으로 만든 일곱 번째 판이 `echo.html` 이었고, **처음으로 긍정 평가를 받았다**:

> *"이거 UI는 심플하고 정말 좋아. 근데 이걸로 음악을 어떻게 생성하는지 모르겠고,
> 내가 누른 점끼리 어떻게 상호작용하는지 잘 안 드러나."*

앞은 칭찬, 뒤는 두 개의 지적이었다. 이 세션은 **그 뒤의 두 문장**에서 시작한다.

## 4. **[측정]** 감사 결과 — 무엇이 빠져 있었나

코드를 열어 **실제로 무엇을 읽고 무엇을 안 읽는지** 대조했다.

### 4-1. 데이터는 다 있었는데 절반만 썼다

`mobile_tonnetz/data/om_bank.json` 을 읽고는 있었지만, 거기서 **`cycles` 하나만** 꺼내고 있었다.

| 같은 JSON 안에 있는 것 | 당시 사용 | 하는 일 |
|---|---|---|
| `cycles` (14개 H₁ 고리) | ✅ 읽음 | 음높이→주기 **룩업표로만** |
| **`om_bits`** (1,680비트 = 120스텝 × 14고리, `zero_rows=0`) | ❌ **안 읽음** | — |
| `generation-algo1.js` (337줄, **바로 옆 폴더**, 검증 완료) | ❌ **안 부름** | — |
| 교집합 규칙 `getIntersectNodes` | ❌ 없음 | — |
| NodePool | ❌ 없음 | — |

`audio-playback.js` 는 순수 Web Audio 합성기로 **연구 내용이 0%** 였다 — 그건 맞다.
스피커지 작곡가가 아니다.

### 4-2. "점끼리 상호작용이 안 드러난다"는 정확한 관찰이었다

**안 드러난 게 아니라 없었다.** 각 점은 자기 주기로 자기 음만 반복하는 **독립 메트로놈**이었고,
점 A와 점 B 사이에 코드상 어떤 연결도 없었다.

### 4-3. 내가 "위상수학적"이라고 써 둔 주석이 사실이 아니었다

```js
PER[p] = 30 + k;   // k = 그 음을 품은 가장 작은 고리의 배열 인덱스
```

`k` 는 `generateBarcode` 가 고리를 뱉은 **배열 순서**다. 위상수학적 의미가 없다.
같은 최소고리를 공유하는 음들이 같은 주기로 **묶이는 것**은 의미가 있지만,
주기 값이 31이냐 41이냐는 임의다.

그런데 코드 주석에는 이렇게 적혀 있었다:

> *"낮은 음이 짧은 주기, 높은 음이 긴 주기로 **저절로 갈렸다** — 내가 정한 게 아니라
> 고리 구성에서 나왔다."*

**배열 순서의 우연을 구조로 읽은 과장**이었다. 같은 문장이 외부에 보낼 프롬프트 문서에도
그대로 옮겨져 있었다.

### 4-4. 그래서 나온 판정 기준

> **연구 데이터를 난수로 바꿔 보라. 귀로 구별이 안 되면 그건 우리 연구가 아니다.**

당시 `echo.html` 은 이 검사를 통과하지 못했다. 주기 묶음만 조금 달라질 뿐,
들어서는 구별할 수 없었다.

### 4-5. **[판단]** 용어 문제에 대한 결론

두 가지를 구분해야 한다.

- **느끼기 전에 설명하기** → 판 4~6 이 죽은 이유. *"이 슬라이더는 α입니다"* 는 6번 거절당했다.
- **느낀 뒤에 이름 붙이기** → 모든 학습이 이렇게 된다. 소리를 듣고, 그 다음에 "그게 5도야".

실제로 한 것은 **셋째**였다: *이름도 안 붙이고 대상까지 없앴다.*

> **용어를 숨기는 것과 메커니즘을 빼는 것은 다르다.**
> 용어를 앞세우지 않은 판단 자체는 유효했다. 잘못은 그걸 **메커니즘을 빼는 핑계로 쓴 것**이다.

## 5. **[판단]** 요구사항 재정의

사용자가 범위를 명확히 잘랐다:

> *"설명을 하거나 이름을 붙일 필요 없어, 다만 플레이어와 상호작용을 통해 생성되는 음악은
> **해당 알고리즘(메커니즘)에 기반해야 해**."*

즉 — **화면에 위상수학을 쓰지 마라. 대신 위상수학이 실제로 돌게 하라.**

이렇게 하면 "의도"가 어디에 담기는지도 정해진다.
이 연구에서 의도를 담는 그릇은 **중첩행렬의 행** — *시각 t에 어떤 고리가 켜져 있나* 이다.
사용자가 그 행을 직접 쓰게 하면 목표가 그대로 성립한다:

```
점을 찍는다  →  그 음을 품은 고리들이 켜진다        = 중첩행렬의 한 행
켜진 고리들에서 뽑는다                              = Algorithm 1
```

**사용자는 중첩행렬을 손으로 쓰고 있는 것**이고, 그게 이 연구의 모든 생성곡의 씨앗이다.

## 6. **[판단]** 작동 원리를 책에서 가져왔다

작업 도중 사용자가 케이트 레이워스 『도넛 경제학』 39쪽 사진을 보내며
*"이것을 참고했으면 좋겠어, **작동원리로 포함**됐으면 좋겠어"* 라고 했다.

> *"경제의 역동성을 이해하는 데 더 지혜로운 출발점은 단순한 **되먹임 회로(feedback loop)
> 한 쌍**으로 요약할 수 있다. (…) 이제 경제를 무슨 **단추나 레버 몇 개로 얼마든지 통제할 수
> 있는 기계**로 보고 그 단추를 찾아 헤매고 다니는 짓은 그만둘 때다. 대신 경제를 영속적으로
> 진화하는 일종의 **복잡계로 보아 돌보고 관리해야** 한다."*

이 문단이 **거절당한 여섯 판의 정체를 정확히 이름 붙인다** — 전부 **단추와 레버**였다.

그리고 그때 짜고 있던 구조도 같은 병에 걸려 있었다. 신호가 **한 방향으로만** 흘렀다:

```
점 → 중첩행렬 → 음.  끝.
```

음이 되돌아오지 않는 **열린 회로**, 즉 반응형 기계였다.

## 7. **[구현]** 최종 설계 — 되먹임 회로 한 쌍

### 7-1. 신호 흐름 (전부 저장소의 실제 코드·데이터)

```
탭 (y좌표)     → label_idx          23개 라벨을 음높이순으로 세로 배치
울리는 음 집합  → 활성도 act[c]       overlap.py : build_activation_matrix (continuous=True)
                                     act[c] = Σ_{n∈c, 울림} rar(n) / Σ_{n∈c} rar(n)
                                     rar(n) = 1 / (n 을 품은 고리 수)   ← 희귀한 음이 무겁다
act ≥ τ=0.35  → 중첩행렬 한 행       overlap.py : build_overlap_matrix (정본 threshold)
그 행          → 음                  generation-algo1.js : algorithm1
                                     = generation.py : _sample_note_at_time 의 검증된 JS 포팅
난 음          → 다시 "울리는 음"     ← 되먹임. 여기가 회로를 닫는 곳이다.
```

마지막 줄이 이 세션의 핵심이다.

### 7-2. 회로 한 쌍

| 회로 | 무엇 |
|---|---|
| **강화 (reinforcing)** | 울린 음 → 고리가 켜짐 → 교집합에서 새 음 → 그 음도 울림 → 고리가 더 켜짐 … |
| **균형 (balancing)** | 새 음의 잔향이 **세대마다 짧아진다** (`RING=10`, `DECAY=0.55` → 4세대에 소멸). 사용자의 점만 자기 주기로 계속 되돌아온다 |

> 그래서 이 화면은 **조작하는 기계가 아니라 돌보는 것**이다.
> 방치하면 꺼지고, 점을 놓아 주면 살아난다.

### 7-3. 주기 — hibari 의 실제 구조로 교체

이전의 `30 + 고리번호`(배열 인덱스)를 버리고, 곡의 실제 메커니즘을 썼다.

hibari 는 한 모듈(32스텝)을 **두 손이 32 · 33 스텝**으로 돌아 매 모듈 한 칸씩 어긋난다
(`history/WK5`, 실측 밀림량 `{0.03125}` = 1/32). `lcm(32,33) = 1056스텝 = 264초`,
즉 **4분 24초마다 재회**한다.

점을 놓는 순서대로 두 손에 번갈아 배정한다. 같은 손의 점은 위상이 잠기고,
다른 손의 점은 천천히 미끄러지다 4분 24초마다 다시 만난다 — **만나면 고리가 켜진다.**

### 7-4. 상수와 그 근거

| 상수 | 값 | 근거 |
|---|---|---|
| `MS` | 250 | 한 스텝 = 8분음표. hibari 와 같은 걸음 |
| `TAU` | 0.35 | `build_overlap_bundle` 의 정본 threshold |
| `SUS` | 12 | 사용자 점이 울리는 스텝 (주기 32의 37.5%) |
| `RING` | 10 | 1세대 생성음의 잔향 — 되먹임의 연료 |
| `DECAY` | 0.55 | 세대마다 잔향 단축 ← **균형 회로** |
| `VOICES` | 2 | 성부 상한. hibari 원 패턴은 3~4지만 성기게 |
| `HANDS` | [32, 33] | hibari 의 두 손 |
| `GEN_W` | 8 | `algorithm1` 호출 창 (§9-2 참조) |

## 8. **[측정]** 검증 — 주장마다 대조군을 돌렸다

코드를 쓰기 전과 쓰는 중에, **브라우저가 아니라 node 로** 규칙만 떼어 돌렸다.

### 8-1. 난이도 곡선 — 고리 하나를 켜려면 음이 몇 개 필요한가

| 고리 | 음 1개 | 음 2개 |
|---|---|---|
| 고리 0 (크기 6) | 0.25 | **0.43** ✅ |
| 고리 2 (크기 7) | 0.27 | **0.54** ✅ |
| 고리 6 (크기 6) | 0.21 | **0.43** ✅ |
| 고리 9 (크기 5) | **0.39** ✅ | — |

→ **보통 음 두 개가 든다.** 희귀한 음(고리 하나에만 속하는 음) 하나로 켜지는 고리도 있다.
혼자서는 안 되고 둘이 되면 뭔가 생긴다 — 좋은 학습 곡선이다.
참고로 **원곡 OM 은 행당 평균 7.33개** 고리가 켜져 있다.

### 8-2. 결정적 대조군 — 균형 회로를 빼면 어떻게 되나

되먹임을 넣고 처음 돌렸을 때 **강화 회로만** 있었다. 결과:

| 점 수 | 고리 궤적 (2분) | 음 | 음높이 |
|---|---|---|---|
| 2 | 7.5 → 7.3 → 7.8 → 7.4 | 960 | 10종 |
| 4 | 7.5 → 7.3 → 7.8 → 7.4 | 960 | 10종 |
| 8 | 9.2 → 8.9 → 9.2 → 9.2 | 960 | 17종 |

**점 2개나 4개나 완전히 똑같다.** 즉시 포화하고 매 스텝 2음으로 고정된다.

> **무엇을 하든 결과가 같으면 사용자 통제감은 0이다.**
> 이건 거절당한 판 2("α가 죽어 있어 미터가 100% 고정")와 **같은 병**이다.
> 기계를 더 정교하게 만들었을 뿐 같은 실패를 반복할 뻔했다.

### 8-3. 균형 회로를 넣은 뒤 — 살아났다

`RING=10, DECAY=0.55` (480스텝 = 2분, 켜진 고리 수를 30초 구간마다):

| 점 수 | 고리 궤적 | 판정 |
|---|---|---|
| **1** | 침묵 480/480 | 고리가 안 켜진다. 메아리만 돌아온다 |
| **2** | 1.9 → 1.8 → 1.3 → **0.3** | **서서히 사그라진다 — 돌봐야 한다** |
| **4** | 4.0 → 3.3 → 1.7 → **2.1** | 유지된다 |
| **8** | 4.5 → 4.9 → 5.3 → **5.9** | 자란다. 침묵 24/480, **포화 0/480** |

포화도 없고 정지도 없다. 숨을 쉰다.

### 8-4. 되먹임이 돌아도 배치가 결과를 지배하는가

되먹임이 모든 걸 평준화하면 사용자 통제가 사라진다. 확인했다 (점 4개, 2분):

| 배치 | 나오는 음 | 특징 |
|---|---|---|
| 낮은 넷 | 52~67, 10종 | **71 이상 0개** |
| 높은 넷 | 67~81, 8종 | **65 이하 0개** |
| 중간 넷 | 52~67, 10종 | |
| 흩어진 넷 | 16종 | 전 음역 |

**어디에 놓느냐가 어느 고리를 켜는지를 정하고, 그게 음을 정한다.**
임의로 만든 매핑이 아니라 교집합 규칙의 결과다.

### 8-5. 브라우저 실측

로컬 서버에서 실제로 눌러 확인:

- 탭 4회 → `play()` 4회 (즉발음) + `add()` 11배치 **70음** 예약, **끊김 없음**
- 두 손이 `[32, 33, 32, 33]` 로 교대 배정
- 고리 4개 활성, 잔향 6개 — 되먹임 살아 있음
- **콘솔 에러 0**
- 스크린샷으로 **함께 울리는 점들이 선으로 이어지는 것** 확인

## 9. **[측정]** 조용히 틀리는 버그 2건

둘 다 **에러 없이 실행되고 결과만 틀리는** 종류다. 대조군을 돌리지 않았으면 못 찾았다.

### 9-1. 되먹임의 라벨 복원이 손실적이었다

`algorithm1` 은 `[시작, 음높이, 끝]` 을 돌려준다 — **라벨 번호가 없다.**
그래서 음높이로 라벨을 되찾고 있었는데, hibari 에는 **음높이 하나에 라벨이 여럿**이다:

| 음높이 | 라벨 수 |
|---|---|
| 57 · 60 · 64 · **69** | 2개씩 |
| 65 | 3개 |

(고유 음높이는 17개인데 라벨은 23개다 — 같은 음높이가 **길이가 달라** 다른 라벨이 된다.)

엉뚱한 라벨이 되먹여지면 **그 라벨이 속한 다른 고리**가 켜진다.
실제로 **높은 점만 놓았는데 낮은 고리 3(`[1,2,3,5]`)·12 가 켜져 전 음역이 열렸다.**
중복 음높이 중 **69는 고음역**이라, 고음 쪽 생성음이 저음 라벨로 잘못 되먹여지는 경로가 열려 있었다.

> **발견 경로**: `getIntersectNodes` 가 활성 고리의 음만 담는데 **저음이 나오는 게 이상하다**고
> 느껴 역추적했다. 증상("음역이 넓다")이 아니라 **불가능한 조합**을 단서로 삼았다.

**수정**: `(음높이, 길이)` 로 복원한다. 라벨은 그 쌍으로 유일하다.

### 9-2. `algorithm1` 을 한 스텝씩 부르면 음 길이가 잘린다

되먹임은 한 스텝의 결과가 다음 스텝의 입력이 되므로 **통째로 계산할 수 없다.**
그래서 `algorithm1` 을 `T=1` 로 부르려 했는데, 내부에 이런 가림이 있다:

```js
if (end > length) { ... }   // length = min(T, instLen.length)
```

`T=1` 이면 `length=1` 이라 **모든 음 길이가 1 스텝으로 잘린다.**
원곡의 음 길이는 **1 · 2 · 5 · 6** 이다 — 리듬이 통째로 사라진다.

**수정**: 창을 8로 주고 `instLen[0]` 에만 값을 넣는다. 길이가 살고 샘플링은 그대로다.

## 10. **[판단]** 자산화 — 개인 통찰로 두지 않았다

이 세션에서 배운 것을 **`CLAUDE.md` 규칙으로 박았다.** 다음 작업에 강제되도록.

근거는 프로젝트가 채택한 **래칫 원리**(harness engineering)다:
*실패하면 증상이 아니라 **실패 계급**을 찾아 **가장 강한 층**에 고쳐 박는다.*

추가한 규칙 두 개:

### 규칙 1 — 단추가 아니라 되먹임 회로

> 앞으로 상호작용 페이지는 **되먹임 회로 한 쌍**으로 짓는다 — 강화 하나, 균형 하나.
>
> **착수 전 물을 것: "이 화면에 강화 회로와 균형 회로가 각각 무엇인가?"**
> 둘 중 하나라도 이름을 댈 수 없으면 그건 또 단추다.

### 규칙 2 — 용어를 숨기는 것과 메커니즘을 빼는 것은 다르다

> **검사법**: 연구 데이터를 난수로 바꿔 보라. 귀로 구별이 안 되면 그건 우리 연구가 아니다.
> 용어는 **느낀 뒤에** 붙인다. 느끼기 전에 설명하면 판 4~6 이 된다.

## 11. 정직하게 남은 것

### 11-1. 아직 확인되지 않은 것

**"재미있어졌다"는 미확인이다.** 확인된 것은 기계적 동작뿐이다
(콘솔 에러 0, 70음 끊김 없이 예약, 고리 4개 활성, 대조군 실측 4조건).
사용자 청취 판정은 아직 받지 않았다.

### 11-2. 설계상 남는 한계 (헤더 주석에 명시함)

1. **고리(H₁)는 미리 계산된 것을 쓴다.** 브라우저에서 위상수학을 다시 풀지 않는다.
2. **정본은 per-cycle τ_c 를 쓰는데** `om_bank.json` 에 τ_c 가 없어 평탄한 τ=0.35 를 쓴다.
3. **한 스텝씩 부르므로** 원본의 `onsetChecker` · `instLen` 스텝 간 이월이 창 경계에서 끊긴다.
   샘플링 자체는 그대로다.
4. **`getIntersectNodes` 는 이름과 달리 교집합이 아니라 공유 가중 합집합이다** —
   활성 고리에 한 번이라도 든 음을 전부 담되, 여러 고리가 공유한 음을 그만큼 겹쳐 담는다.
   균등추출이 곧 공유 가중이라 따로 가중치를 넣을 곳이 없다. 원 설계가 그렇다.

한계를 **숨기지 않고 코드 헤더에 적어** 다음 사람이 오해하지 않게 했다.

### 11-3. 이 세션에서 고치지 못한 더 큰 문제

- **백엔드가 없다.** `arena/` 에서 받은 20표가 `localStorage` 에만 남아 아무에게도 안 보인다.
- **100명 참여 목표**에 저장소가 없다. GitHub Pages 는 정적이라 구조적으로 불가능하다.
